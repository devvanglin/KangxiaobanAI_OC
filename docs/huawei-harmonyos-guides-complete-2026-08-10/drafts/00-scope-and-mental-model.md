## 1. 文档定位

### 1.1 目标

这套文档要把体量巨大的 HarmonyOS 官方指南转换为三种可复用资产：

1. **可审计的知识索引**：能回答“左侧菜单中的每一个正文入口是否真的打开过、读过、记录过”。
2. **可检索的工程知识**：能按模块、Ability、ArkUI、状态管理、系统能力、工具、测试、体验等维度找到结论和官方来源。
3. **可执行的 AI 编程约束**：让 Codex、Claude 等工具在改代码之前知道要核对什么，在改代码时知道哪些边界不能猜，在交付时知道哪些验证不能省略。

### 1.2 主要读者

- 初学 HarmonyOS、ArkTS、ArkUI 的开发者；
- 维护现有 HarmonyOS NEXT 项目的工程师；
- 使用 Codex、Claude 或其他代码代理进行实现、审查和排障的人；
- 需要判断“官方文档怎么说”“当前项目到底怎么做”“代码是否真的验证过”的评审者。

### 1.3 它不是什么

- 不是对官网长段文字的镜像或复制；
- 不是脱离版本和工程配置的 API 百科；
- 不是把示例代码原样粘贴进生产项目的理由；
- 不是当前项目已经具备网络、权限、分布式、AI 或真实后端能力的证明；
- 不是一次抓取完成后永远不会过期的静态快照。

官方页面负责给出正式定义、接口契约、适用版本和限制；本地文档负责建立导航、归纳关系、工程检查项和项目适配说明。遇到冲突时，应回到当前官方页面与当前工程配置重新核对。

另有 **5,720 个 UI 节点**。两者不是同一个概念：

- `UI 节点` 包含分组标题、可展开父节点以及正文入口；

- 因此，完成 5,720 个 UI 节点的展开与遍历，是发现范围的条件；
- 完成 5,694 个正文链接的逐页进入与阅读，才是正文覆盖的主体条件。

数量关系为：

```text
45 + 4,811 + 757 + 23 + 58 = 5,694 个正文链接
5,720 个 UI 节点 >= 5,694 个正文链接
```

## 3. “所有内容完整读完”的完成判据

### 3.1 四层完成模型

全量任务必须同时完成四层，而不是只完成其中一层。

#### A. 发现完整

- 左侧菜单的所有可展开节点都被展开；
- 懒加载后的子节点被继续遍历，直到没有未展开分支；
- 每个 UI 节点都有稳定的层级路径；
- 每个正文链接都记录原始 URL 和规范化 URL；
- 能解释 UI 节点数与正文链接数的差异；
- 网站更新造成的新增、删除、重命名和移动有差异记录。

#### B. 进入完整

- 每一个正文链接都实际打开；
- 页面成功加载到正文，而不只是导航高亮或空壳；
- 重定向、登录提示、地区限制、404、脚本错误和加载超时被单独记录；
- 同一正文被多个菜单入口引用时，保留入口关系并标记内容去重，不能静默跳过；
- 失败页面经过重试，仍失败的进入明确的待处理清单。

#### C. 阅读完整

每一页至少要提取并理解以下内容（页面没有的项目可标记为“不适用”）：

- 页面解决的问题和适用场景；
- 前置条件、SDK/API 版本、设备形态和模块要求；
- 核心对象、接口、配置项和调用关系；
- 生命周期、线程、异步、回调或错误处理要求；
- 权限、隐私、安全、资源释放和数据边界；
- 示例代码表达的最小模式，而不是只看最终代码块；
- 限制、注意事项、废弃/不推荐信息和替代方案；
- 与上下游页面的关系；
- 对当前工程是否适用，以及还需哪些验证。

页面中的页签、折叠面板、代码语言切换、图片说明、表格、提示框和“相关链接”不能因为默认不可见而漏读。

#### D. 理解与复核完整

- 每页都有简短摘要和结构化标签；
- 关键主题有跨页面综合，而不是 5,694 份互不相连的摘要；
- 冲突内容按版本、场景或 API 代际解释，不能强行合并；
- 随机抽样能从本地结论回到准确的官方页面；
- 高风险主题（权限、隐私、发布、签名、数据、医疗/健康、账号、支付等）有二次复核；
- 全量台账中不存在“未访问”“加载失败未处理”“只抓标题未读正文”的记录。

### 3.2 建议的链接级台账字段

每一个正文链接应有一条记录，至少包含：

| 字段 | 含义 |
|---|---|
| `node_id` | 本地稳定编号 |
| `section` | 入门 / 开发 / 工具 / 测试 / 体验建议 |
| `menu_path` | 从一级分区到页面的完整菜单路径 |
| `title` | 页面标题 |
| `source_url` | 菜单中发现的原始链接 |
| `canonical_url` | 跳转后的规范链接 |
| `discovered_at` | 发现时间 |
| `opened_at` | 实际打开时间 |
| `http_or_ui_status` | 正常、跳转、404、需登录、超时、脚本失败等 |
| `read_status` | 未访问、已打开、已读、已摘要、已复核、阻塞 |
| `content_fingerprint` | 用于识别重复正文或页面变化的指纹 |
| `version_scope` | 页面声明或核对出的版本/API 范围 |
| `summary` | 对页面目的和主干规则的简述 |
| `key_constraints` | 权限、生命周期、设备、线程、释放、限制等 |
| `project_relevance` | 适用、不适用、部分适用、待验证 |
| `evidence_links` | 关联官方页面或本地章节 |
| `reviewer` / `reviewed_at` | 复核者和复核时间 |

### 3.3 阅读状态必须互斥、可审计

推荐状态机：

```text
未发现
  -> 已发现
  -> 已打开
  -> 已完整阅读
  -> 已结构化摘要
  -> 已复核

任一步骤都可能 -> 阻塞
阻塞解决后回到对应步骤继续
```

禁止把以下情况记为“已完整阅读”：

- 只读取标题、摘要或搜索结果片段；
- 只抓取 HTML，但没有处理动态折叠内容；
- 页面加载失败后凭标题猜内容；
- 只让模型生成概括，却没有保留页面对应关系；
- 只读一个主题的入口页，未进入它的子页面；
- 把重复 URL 和重复正文混为一谈后直接删记录；
- 只统计点击次数，不核验实际正文是否切换。

### 3.4 最终完成条件

只有同时满足下列条件，才可以写“官网左侧菜单全部阅读完成”：

```text
发现覆盖率 = 已发现 UI 节点 / 5,720 = 100%
正文进入率 = 成功打开或有明确阻塞记录的正文链接 / 5,694 = 100%
正文阅读率 = 已完整阅读正文链接 / 5,694 = 100%
摘要覆盖率 = 已结构化摘要正文链接 / 5,694 = 100%
未解决失败数 = 0
未归因差异数 = 0
高风险页面复核率 = 100%
```

如果官网在执行期间发生更新，应同时保存“基准快照完成率”和“当前官网补差状态”，不能悄悄用新的分母覆盖旧进度。

## 4. 写作证据标签：官方事实、解释、项目适配必须分开

这套标签既用于人类阅读，也用于给 Codex、Claude 提供上下文。每一个会影响实现的结论，都应能看出它来自哪里、适用到哪里、验证到什么程度。

### 4.1 `[官方事实]`

用于可以直接从当前官方页面、当前官方配置说明或当前 API 契约定位的内容。

写法要求：

- 保留官方页面链接；
- 记录核对日期；
- 涉及接口时记录 API/SDK 范围；
- 尽量转述，不复制长段原文；
- 保留必要的官方专有名词、类型名、方法名和配置键；
- 如果页面写明“不推荐”“废弃”“仅某设备支持”，必须一并保留。

示例格式：

```text
[官方事实][核对日期：YYYY-MM-DD][API 范围：待填]
某能力要求在模块配置中声明对应项，并在运行时处理授权结果。
来源：<官方页面 URL>
```

### 4.2 `[解释]`

用于把多个官方页面组织成更容易理解的心智模型、调用链或决策规则。

解释必须满足：

- 不冒充官方原句；
- 不扩大官方承诺；
- 清楚说明它是归纳、类比或工程建议；
- 能列出支撑它的一个或多个官方来源；
- 如果存在例外，明确指出例外所在的版本、设备或场景。

示例格式：

```text
[解释]
可以把 UIAbility 看作窗口化应用体验的生命周期入口，但页面状态、业务状态和持久化状态不应因此全部放进 Ability。
依据：<来源 A>、<来源 B>
```

### 4.3 `[项目适配]`

用于说明官方模式在当前 `KangxiaobanAI` 工程中应如何落地。

项目适配必须同时引用：

- 当前工程配置或源码证据；
- 对应的官方页面；
- 适用的 SDK、模块、设备形态与状态管理代际；
- 已完成和未完成的验证。

示例格式：

```text
[项目适配][KangxiaobanAI][API 24][phone/tablet/2in1]
当前业务壳采用 ArkUI V2 与 HDS；新增核心组件默认延续 @ComponentV2，不能因为附近旧样例使用 V1 就直接混入 V1 装饰器。
工程证据：AGENTS.md 与当前源码配置
官方依据：<待链接到对应 V2 页面>
验证：静态配置已确认；具体改动仍需精确构建与设备验证
```

### 4.4 `[验证状态]`

建议统一使用以下词汇，避免“写了代码”等于“已经可用”：

| 标签 | 含义 |
|---|---|
| `Implemented` | 本地存在可追踪代码路径 |
| `Build-verified` | 指定产品/模块/模式的构建有成功证据 |
| `Device-verified` | 在声明的真实设备形态上实际验证 |
| `Service-verified` | 与真实 AGC/后端/外部服务完成验证 |
| `Planned` | 只有方案或目标，没有当前实现 |

一次结论可以有多个标签，但不能用较弱的证据冒充较强的证据。例如，静态检查通过不等于设备验证，页面能显示不等于真实服务调用成功。

### 4.5 引用与转述规则

- 优先用自己的语言总结“目的、条件、步骤、限制、错误与验证”；
- 代码只保留理解模式所需的最小片段；
- 长示例应链接回官方页面，不在本地全文复制；
- 同名 API 在不同版本有差异时，分别记录，不拼成一个不存在的“通用接口”；
- 官方营销描述与工程契约分开；能力宣称必须落实到配置、API、权限、设备和验证；
- 页面缺少关键信息时写“官方页面未在当前段落说明 / 待交叉核对”，不要补猜。

## 5. 人类阅读路线

### 5.1 15 分钟快速建立方向

适合刚接触项目、准备开工的人：

1. 读本文件第 0～4 节，理解范围和证据边界；
2. 读第 7 节的 HarmonyOS 工程心智模型；
3. 读第 9 节当前项目适配基线；
4. 根据任务类型跳到对应专题文档；
5. 开始改代码前执行第 10 节的 AI/人类共同工作协议。

目标不是背 API，而是先回答五个问题：

```text
我改的是哪个产品和模块？
代码运行在哪个生命周期和设备形态？
状态由谁拥有，数据来自哪里？
调用系统能力需要哪些配置、权限和释放动作？
我准备用什么证据证明改动真的成立？
```

### 5.2 两小时工程导览

适合新成员或需要全面理解架构的人：

1. 从应用、产品、模块和包结构开始；
2. 沿启动链追到 UIAbility、WindowStage、根页面和导航壳；
3. 学习 ArkTS、ArkUI、V2 状态管理和组件通信；
4. 学习资源、国际化、深浅色和响应式布局；
5. 学习系统 Kit 的配置—权限—调用—错误—释放闭环；
6. 学习构建、签名、调试、测试、性能和发布；
7. 回到当前项目逐项映射，不适用的能力明确标记。

### 5.3 按任务查阅

| 任务 | 第一批应查内容 | 必须补查 |
|---|---|---|
| 新页面/新组件 | ArkUI 组件、V2 状态、导航、资源 | 响应式、无障碍、动效、性能 |
| 新 Ability/Extension | 应用模型、生命周期、模块配置 | 启动入口、后台规则、权限、释放 |
| 新系统能力 | 对应 Kit 指南与 API | 权限、隐私、错误码、设备支持、服务配置 |
| 新数据层 | 数据管理、网络、序列化 | 并发、缓存、迁移、加密、登出清理 |
| 多设备适配 | 一次开发多端部署、窗口与断点 | 输入方式、安全区、折叠/旋转、性能 |
| 自由流转/分布式 | 自由流转与相关 Kit | 设备发现、身份、数据一致性、失败恢复 |
| 构建失败 | 构建系统、包管理、命令行工具 | SDK/JDK/签名环境、第一因错误 |
| 发布上线 | 构建、签名、发布 | 隐私、安全、版本、兼容、商店要求 |
| UI 审查 | 体验建议、ArkUI、HDS/设计系统 | 深浅色、大字体、键鼠、读屏、性能 |

### 5.4 评审者路线

评审者不需要按 5,694 页顺序重新读一遍，但应抽查：

- 结论是否有可点击的官方来源；
- 来源日期和 SDK 范围是否匹配当前工程；
- `[官方事实]`、`[解释]`、`[项目适配]` 是否混淆；
- 示例能否映射到当前模块和状态管理代际；
- 构建、设备、服务验证是否被正确区分；
- 权限、隐私、生命周期、资源释放和失败状态是否完整。

## 7. HarmonyOS 整体工程心智模型

本节是 `[解释]`：它把官方指南中分散的主题组织成一张工程地图，方便理解和检索。具体接口、配置键、版本和限制仍要回到对应官方页面核对。

### 7.1 先建立三个坐标系

理解任何 HarmonyOS 代码，都应同时放进三个坐标系。

#### 坐标一：交付与配置

```text
应用（bundle / AppScope）
  -> 产品与构建配置（product / build mode / SDK / signing）
  -> 模块（entry / feature / HAR / HSP / 其他模块形态）
  -> 模块组件与资源（Ability / Extension / pages / resources）
  -> 构建产物、安装、发布
```

它回答：代码属于谁、如何打包、装到哪里、向系统声明了什么。

#### 坐标二：运行与生命周期

```text
系统启动组件
  -> Ability / Extension 生命周期
  -> WindowStage / 窗口
  -> 根页面与导航容器
  -> ArkUI 组件树
  -> 状态变化驱动局部刷新
  -> 用户事件调用领域逻辑或系统 Kit
  -> 异步结果更新状态
  -> 页面/组件销毁时释放监听器、定时器和系统资源
```

它回答：谁先创建、谁拥有状态、谁接收事件、谁负责清理。

#### 坐标三：用户体验与业务真相

```text
用户目标
  -> 信息架构与导航
  -> 页面状态（加载/空/错误/离线/无权限/成功）
  -> 业务规则与数据来源
  -> 系统能力和外部服务
  -> 反馈、可访问性、性能与失败恢复
```

它回答：界面为什么存在、用户看到的状态是否真实、失败后能否恢复。

只看其中一个坐标系会产生典型误判：页面画出来了但模块没配置；API 调用了但生命周期没有释放；本地数组更新了却向用户显示“服务提交成功”。

### 7.2 八层工程地图

```text
┌────────────────────────────────────────────┐
│ 8. 交付与治理：构建、签名、发布、安全、隐私、质量 │
├────────────────────────────────────────────┤
│ 7. 工具与验证：DevEco、命令行、调试、测试、性能   │
├────────────────────────────────────────────┤
│ 6. 设备与连续性：多端适配、窗口、自由流转、分布式  │
├────────────────────────────────────────────┤
│ 5. 系统与服务能力：各类 Kit、权限、错误、资源释放  │
├────────────────────────────────────────────┤
│ 4. 数据与领域：模型、存储、网络、缓存、并发、会话  │
├────────────────────────────────────────────┤
│ 3. UI 与交互：ArkUI、状态、导航、资源、动效、无障碍│
├────────────────────────────────────────────┤
│ 2. 应用运行模型：Ability、Extension、窗口、生命周期│
├────────────────────────────────────────────┤
│ 1. 工程与包：App、产品、模块、依赖、配置、产物     │
└────────────────────────────────────────────┘
```

上层依赖下层提供的事实，但责任不能倒灌。例如：UI 可以请求用例执行登录，但 UI 不应因此负责构造传输 DTO、持有重试策略和决定租户授权。

### 7.3 第一层：应用、产品、模块与产物

这是所有开发的地基。

要先分清：

- 工作区里可能有多个彼此独立的应用或样例；
- 一个应用可以有产品、构建模式和多个模块；
- 模块名称不能可靠表示模块类型，权威信息在当前配置；
- entry/feature 等交付模块、HAR 共享库、HSP 共享包承担不同边界；
- AppScope、根构建配置、模块配置、依赖清单和资源共同决定最终产物；
- 页面文件存在不代表已经注册，Ability 类存在不代表系统配置已经声明；
- 能构建一个模块不代表所有产品都构建成功。

工程推理顺序应是：

```text
定位顶层项目
  -> 读根 build-profile 与包清单
  -> 读 AppScope/app.json5
  -> 读目标模块 module.json5 / build-profile / 包清单
  -> 确认 target/compatible SDK、runtime OS、deviceTypes、module type
  -> 确认入口、页面、路由、权限、Extension 和依赖
```

### 7.4 第二层：Ability、Extension、窗口与生命周期

Ability/Extension 是系统与应用代码之间的重要运行边界。理解一个功能时，不要只看某个回调里的几行代码，要追踪完整生命周期：

```text
系统为何创建它？
  -> 配置中的声明是什么？
  -> 入口类和 srcEntry 在哪里？
  -> 创建了哪个窗口或后台能力？
  -> 根内容如何加载？
  -> 前后台、配置变化、窗口变化如何处理？
  -> 谁注册监听、持有会话或打开资源？
  -> 对称的注销、停止、关闭在哪里？
```

生命周期所有权原则：谁创建长期资源，谁就要能在确定的生命周期中释放它。监听器、定时器、播放器、相机、传感器、节点、PixelMap、数据库游标或网络会话都不能只写“启动路径”而没有“停止路径”。

### 7.5 第三层：ArkTS、ArkUI 与状态驱动界面

ArkUI 是声明式 UI。核心关系不是“调用一个函数把界面重画”，而是：

```text
状态是事实
  -> build 描述该状态下的界面
  -> 用户或异步事件改变状态
  -> 框架更新受影响的 UI
```

需要分开的状态至少有：

- **应用/会话环境状态**：当前用户、租户、全局环境、窗口信息；
- **功能状态**：列表、筛选、分页、当前业务流程；
- **页面临时状态**：选中项、表单草稿、弹层显示；
- **持久化状态**：Preferences、数据库、文件或远程服务中的数据；
- **派生状态**：由其他状态计算得出，不应重复存储并产生不一致。

同时要确认 ArkUI 状态管理代际。V1 与 V2 的装饰器、传参和可观察模型不能仅凭外观相似就随意混用。样例采用旧代际时，只能提炼概念，再转换成当前项目的同代实现。

高质量 ArkUI 代码还应做到：

- `build()` 和热点 builder 中不做昂贵业务计算；
- 列表使用稳定身份与合适的懒加载/复用机制；
- 自定义点击区域具备语义、焦点和键盘操作；
- 动效可中断、与真实状态一致，并考虑减少动态效果；
- 异步操作有加载、失败、重试、取消和超时，不提前显示成功。

### 7.6 导航不是“页面跳转函数”的集合

导航应先划分边界：

- 应用外部入口、认证壳切换、业务内层级导航、页签切换、局部详情、弹层/Sheet、跨模块路由承担不同职责；
- 路由表、页面注册、builder、参数类型、返回行为和深链入口必须一致；
- 一个页面能被 push 出来，不代表它适合作为独立系统入口；
- 局部工作区分支不一定需要注册成全局路由；
- 返回手势、系统返回、窗口形态变化和进程重建都要考虑。

应画出真实导航图，再决定使用传统 router、Navigation/NavPathStack、Tab、局部条件渲染、Sheet 或 Cover，而不是看见“下一个界面”就随便选一种跳转 API。

### 7.7 资源、主题、国际化与多端布局

HarmonyOS UI 不是只在一个固定分辨率、固定语言和固定输入方式上运行。

需要作为同一个设计问题处理的因素包括：

- 资源引用与限定目录；
- 深色/浅色及系统主题；
- 文本扩展、国际化和大字体；
- phone、tablet、2in1 等设备形态；
- 窗口缩放、旋转、分屏、折叠状态；
- 状态栏、导航指示条、挖孔、键盘等安全区；
- 触摸、鼠标、键盘、焦点和读屏；
- 横竖屏与连续窗口尺寸变化。

响应式设计应优先围绕“可用宽度和内容需求”建立断点，而不是把设备名称硬编码成布局逻辑。视觉画布可以延伸到系统区域，交互内容仍必须消费真实安全区数据。

### 7.8 第四层：领域、数据与异步状态

建议的数据方向：

```text
ArkUI Page/Component
  -> ViewModel / Store
  -> UseCase / Domain Service
  -> Repository Interface
  -> RemoteDataSource / LocalDataSource
```

关键边界：

- API DTO 与领域模型分开；
- 未知值、缺失值、单位、时区和枚举兼容显式建模；
- 分页、缓存新鲜度、冲突、离线、幂等和错误是仓库契约的一部分；
- Session、Tenant、CurrentUser、UserRole 是明确模型，显示字符串不是授权；
- 敏感数据最小化、本地保护、日志脱敏和登出/切租户清理要落到所有者；
- 本地 FakeRepository 与真实仓库实现相同接口，便于替换而不重写 UI。

界面上的“成功”必须对应真实的状态跃迁：本地模拟只能写成演示结果，服务提交要等服务确认；网络未完成时应显示进行中，而不是乐观地伪造最终事实。

### 7.9 第五层：系统 Kit 与服务能力

接入任一系统能力都应完成一个闭环：

```text
能力与版本确认
  -> 模块/应用配置
  -> 权限与用户说明
  -> 运行时能力/授权检查
  -> API 调用
  -> BusinessError/异常/取消处理
  -> 前后台与设备变化处理
  -> 资源释放
  -> 真机或真实服务验证
```

不同能力可能还需要 AGC、证书、应用市场配置、服务开通、真实账号、硬件或网络条件。把 API 写进代码并成功编译，只能证明很小的一部分。

对账号、位置、相机、推送、健康、地图、支付、AI 等敏感能力，应额外回答：

- 为什么需要收集或访问；
- 最小权限和最小数据是什么；
- 拒绝后是否仍可使用核心功能；
- 数据发送到哪里、保存多久、如何删除；
- 通知、日志、剪贴板和截图会不会泄漏；
- 高影响结果是否需要人工确认和审计。

### 7.10 第六层：一次开发多端部署、自由流转与分布式

这三类概念不应混成一句“支持多设备”。

- **多端部署**关注同一产品如何根据屏幕、窗口、输入和设备能力提供合适体验；
- **自由流转/连续性**关注任务或状态如何在设备间迁移、接续或协同；
- **分布式能力**还涉及设备身份、发现、连接、数据一致性、权限和断连恢复。

产品页面在 phone/tablet/2in1 上能自适应，不等于已经实现跨设备流转；项目中出现设备选择 UI，也不等于系统级分布式能力已经接通。必须找到真实配置、API、权限、会话和设备验证证据。

### 7.11 第七层：开发工具不是实现细节的附录

工具链决定代码能否被准确验证：

- DevEco Studio 与 SDK/JDK 环境；
- ohpm 依赖与本地 `file:` 包；
- Hvigor 构建任务、产品、模块和构建模式；
- 模拟器、预览器与真实设备的能力差异；
- 日志、断点、Profiler、Inspector 和命令行工具；
- 签名、证书和本地/CI 注入；
- 构建缓存与生成文件的边界。

排障时应读第一个因果错误，不要把删缓存当默认修复。环境变量、SDK 路径、JBR、签名文件和设备连接问题要与 ArkTS 源码错误分开判断。

### 7.12 第八层：测试、性能、发布和治理

完整验证是分层的：

```text
结构/配置检查
  -> 语法与静态检查
  -> 单元/组件/集成测试
  -> 指定产品和模式构建
  -> 真机 UI、导航、权限、硬件验证
  -> 真实服务端到端验证
  -> 性能、稳定性、安全、隐私与发布检查
```

每层回答的问题不同，不能相互替代：

- 模板测试通过，不代表业务规则正确；
- HAP 构建成功，不代表真实设备表现正确；
- 设备页面打开，不代表后台服务、推送或账号能力已验证；
- 一次成功，不代表弱网、取消、重试、前后台和资源泄漏场景可靠。

性能工作要先测量再修改，关注启动、首帧、列表、动画、内存、后台资源、预加载和长期运行。发布还要核对版本、签名、混淆、权限、隐私声明、兼容性、升级和回滚。

5. 以当前 SDK 和工程证据完成适配与验证。

## 9. 当前 `KangxiaobanAI` 的项目适配基线

本节是 `[项目适配]`。以下内容来自当前工作区的项目约束与已验证配置基线；实现任务仍应重新读取当前源码，防止后续漂移。

### 9.1 项目身份

- 默认交付目标是 `KangxiaobanAI`；其他顶层项目主要是架构、UI 技术或 Kit 样例；
- 产品是 HarmonyOS NEXT 原生智慧养老工作台；
- 当前成熟度是高保真本地交互原型，不是已连接真实后端、真实 AI 或生产临床系统；
- 当前 target SDK 为 `6.1.1(24)`，compatible SDK 为 `6.1.0(23)`；
- 主模块为 `products/entry` 下的 entry 模块；
- 设备形态为 `phone`、`tablet`、`2in1`。

因此，任何从官方页面或本地样例提取的模式，都要先问：它是否适用于 target API 24、最低 compatible API 23、entry 模块和这三种设备形态？

### 9.2 启动与导航

当前运行主链：

```text
KanxiaobanAbility
  -> WindowStage.loadContent('pages/LoginPage')
  -> 登录壳本地模拟
  -> router.replaceUrl('pages/MainPage')
  -> MainPage 的 HdsNavigation / NavPathStack 业务壳
```

当前固定边界：

- 传统 router 只用于认证壳的登录/退出切换；
- 应用内业务流优先使用共享 `NavPathStack`；
- 局部详情、Sheet、Cover 和工作区分支按现有所有权延续；
- 不经产品批准，不增加新的一级 Tab；
- 新增路由时必须同步模块 route map、route name、source、builder 与参数类型。

### 9.3 ArkUI V2 与 HDS

当前核心源码采用 ArkUI V2，并使用 `@kit.UIDesignKit` 的 HDS 导航、页签与系统材质能力。

新增核心组件默认延续：

- `@ComponentV2`；
- `@Local`；
- `@Param` / `@Require`；
- `@Event`；
- `@Provider` / `@Consumer`；
- `@ObservedV2` / `@Trace`；
- 只把真正应用级环境放进 `AppStorageV2`。

不能因为本地某个 API 17/20 样例使用 V1，就把 V1 装饰器直接混进当前核心产品。HDS 已是现有设计系统，也不应为了“更熟悉”而无理由替换成普通 ArkUI 壳。

### 9.4 响应式与安全区

- 布局按实时窗口断点判断，不硬编码设备名称；
- 状态栏、导航指示条、键盘等高度来自实时环境模型；
- 视觉画布的沉浸扩展与交互内容的安全区消费分开；
- phone/tablet/2in1、旋转、窗口缩放、深浅色、大字体、键鼠焦点和返回手势都应按改动范围验证；
- 窗口/系统监听器应有对称清理路径，新增监听之前先补清现有所有权。

### 9.5 数据与服务真实性

当前登录、居民、健康、任务、设备、消息、医生、管理员和 AI 交互主要是本地 mock 或定时器模拟。文档和 UI 必须区分：

- 本地实现；
- 构建验证；
- 真机验证；
- 真实服务验证；
- 计划中的架构。

新增真实数据能力时，优先保持 UI 行为，再按 `FakeRepository -> ViewModel/Store -> UseCase -> Repository 接口 -> 真实数据源` 的顺序提取，不要把网络、权限、DTO、重试和大段 mock 数据继续堆进现有大型页面文件。

### 9.6 样例使用规则

本地样例库的正确用途是“查找同代最小模式”，不是“整页复制”。使用前必须核对：

- 样例的 target/compatible SDK；
- 模块类型和设备形态；
- ArkUI V1/V2 代际；
- 是否依赖真实服务、权限、证书或硬件；
- 是否包含旧 API、上游说明或历史配置；
- 如何转换为当前产品的 HDS、V2、导航和状态所有权。

## 10. 人类与 AI 共同执行的开发协议

### 10.1 改动前

1. 确认目标顶层项目，不把样例当交付产品；
2. 记录工作树状态，保护用户已有改动；
3. 读取根与模块配置，确认 SDK、模块类型、设备和依赖；
4. 从 Ability 入口追到根页面、导航和目标功能；
5. 确认 ArkUI 状态管理代际、HDS、资源和安全区所有者；
6. 搜索当前工程与本地样例中的同代模式；
7. 打开当前官方页面核对 API、配置、权限和限制；
8. 定义最小修改边界和验收场景。

### 10.2 改动中

- 保持现有依赖方向和状态所有权；
- 配置、代码、资源、路由和权限一起维护；
- 异步状态真实反映 `idle/loading/success/error/cancelled`；
- 不在 UI 中伪造真实服务成功；
- 不在日志、通知或示例中泄露敏感数据和签名信息；
- 注册监听/定时器/资源时同时设计释放路径；
- 不顺手重构无关项目或清理用户生成文件；
- 代码注释说明非显然约束，不复述每一行语法。

### 10.3 改动后

1. 检查 diff，只保留任务相关变化；
2. 检查配置、路由、资源和依赖一致性；
3. 运行聚焦测试，避免用模板断言冒充业务测试；
4. 构建精确产品/模块/模式；
5. UI、导航、权限、系统能力变更进行对应设备验证；
6. 外部服务变更进行真实服务验证；
7. 记录未验证项、回退路径和剩余风险；
8. 稳定架构事实变化时同步维护项目约束文档。

## 11. 常见误区与纠偏

| 误区 | 为什么错 | 正确做法 |
|---|---|---|
| 打开 ArkTS 入口页就算读完官网 | 左侧仍有数千正文和多级子菜单 | 以 5,720 UI 节点和 5,694 正文链接台账验收 |
| 抓到 URL 就算读过 | 抓取不等于页面成功加载和理解限制 | 分开记录发现、打开、阅读、摘要、复核状态 |
| 官方示例能直接复制 | SDK、模块、设备和 V1/V2 可能不同 | 选同代最小模式并做当前项目适配 |
| 编译通过就是能力可用 | 权限、服务、硬件、账号和设备行为未证明 | 区分 Build/Device/Service 验证 |
| UI 显示成功就算服务成功 | 本地状态可能没有持久化或服务确认 | 让反馈对应真实异步状态和持久化结果 |
| 所有状态都放全局存储 | 造成生命周期模糊和业务耦合 | 区分应用、功能、页面、持久化和派生状态 |
| 每个详情都注册全局路由 | 局部状态和返回语义会被放大 | 先画导航所有权，再选 Navigation/Sheet/Cover/局部分支 |
| 沉浸式等于忽略安全区 | 视觉延伸不代表按钮可被系统区域遮挡 | 画布与交互内容分别处理 |
| 加了监听就完成能力接入 | 未释放会导致泄漏或重复回调 | 设计对称 lifecycle cleanup |
| 删缓存是构建排障第一步 | 可能掩盖 SDK/JDK/签名或源码首因 | 先读第一因错误并分层定位环境与代码 |
