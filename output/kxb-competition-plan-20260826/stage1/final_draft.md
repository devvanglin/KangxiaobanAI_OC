## 一、执行摘要

本方案回答一个问题：**拿什么上场比赛，怎么演，怎么落地。**

比赛展示一条完整叙事线：**AI 入院评估 → 照护计划选择 → 毫米波持续监护（跌倒/呼吸/心率）→ 摄像头+VL 模型行为识别 → 告警处置闭环**。四个环节串成"从入院到日常守护"的完整故事。

三个关键准信：

1. **UI 底座已就绪。** 鸿蒙端 App（手机+平板/2in1 宽屏三形态）已具备登录、工作台、老人档案、健康列表、设备列表、消息、AI 对话页、医生入院评估工作台（含评估→建议→计划选择→知情确认的完整 UI 骨架）。当前为高保真本地原型，数据全部为 mock。
2. **毫米波是现成的真家伙。** 工作区已沉淀海凌科 60GHz 雷达（R60ABD1 睡眠呼吸心率 + R60AFD1 跌倒检测）完整 MQTT 协议、Python 接入 Demo、养老院多房间部署方案。比赛现场可跑真数据。
3. **摄像头+VL 行为识别是增量模块。** 采用边缘部署开源视觉语言模型（Qwen2.5-VL 类）做行为识别，与毫米波交叉验证降低误报。按本方案路线图赛前完成演示级部署。

文档覆盖：现状准信（第二章）、三大场景设计（第四至六章）、端到端工作流（第七章）、安全与隐私合规（第八章）、数据集建设（第九章）、演示路线图与风险预案（第十章）。

## 三、总体架构与展示叙事主线

### 3.1 一句话架构

**鸿蒙端（三形态 App）+ 边缘感知层（毫米波雷达×2 + 摄像头）+ 局域网服务层（EMQX 消息总线 + 后端网关 + AI 推理服务）**，全部跑在比赛局域网内，不依赖公网，演示稳定可控。

### 3.2 系统分层

| 层 | 组件 | 职责 |
|----|------|------|
| 端侧 | KangxiaobanAI（phone/tablet/2in1） | 入院评估对话、计划选择、实时监护看板、告警处置 |
| 感知层 | R60ABD1 睡眠雷达（卧室）、R60AFD1 跌倒雷达（卫生间）、网络摄像头 | 呼吸/心率/睡眠、跌倒检测、视觉行为识别 |
| 服务层 | EMQX Broker（MQTT）、后端网关（Python/FastAPI）、VL 推理服务（GPU 主机） | 设备数据汇聚、房间路由、告警判定、AI 对话代理 |
| 数据层 | 房间-设备绑定表、评估会话存储、事件库 | 台账、评估记录、告警留痕 |

### 3.3 比赛叙事主线（评委看到的六分钟故事）

1. 老人入住 → 护理员在鸿蒙平板打开医生工作台，AI 以对话方式完成入院评估（约 90 秒）。
2. AI 生成护理等级建议与 A/B/C 三套照护计划 → 医生选择并确认（约 60 秒）。
3. 镜头切到卧室：毫米波雷达实时推送呼吸/心率/睡眠状态到 App 看板，数值滚动（约 60 秒）。
4. 演示跌倒：志愿者在雷达下缓慢倒地 → fallStatus=1 → App 弹出红色告警 + 摄像头 VL 复核确认"跌倒姿态" → 双传感器交叉验证置信告警 → 护理员标记处置（约 90 秒）。
5. 收尾：事件回流档案，计划自动生成复查建议，闭环（约 60 秒）。

## 四、场景一：AI 入院评估对话与照护计划选择

### 4.1 业务流程

入院评估采用**对话式结构化采集**：AI 扮演评估助手，按量表逐项提问，护理员代老人作答（老人参与度视认知状态调整）。评估维度对齐现行养老机构通行做法：

| 评估维度 | 参考量表 | 输出 |
|---------|---------|------|
| 日常生活活动能力 | Barthel 指数（进食、洗澡、修饰、穿衣、控便、如厕、转移、行走、上下楼梯） | 0-100 分，四级分级 |
| 跌倒风险 | Morse 跌倒评估 | 低/中/高危 |
| 认知状态 | 简易智能状态检查（MMSE，或简化版） | 认知分级 |
| 营养与吞咽 | 简化营养初筛（对应现有"入住健康初筛"维度） | 初筛标记 |

**关键设计：AI 不直接下诊断结论，只输出结构化评估结果 + 分级建议 + 计划选项，最终由医生确认。**这既是安全底线，也是答辩时"人机协同"的加分点。现有 `WideDoctorAdmission` 的评估维度（0-4 五级分级）已与此对齐，改造量集中在数据源从本地状态换成模型输出。

### 4.2 技术实现

1. **模型接入**：局域网部署开源对话模型（Qwen 系列 32B/72B 或比赛算力允许的规模），OpenAI 兼容 HTTP 接口。App 端走 hermes 已验证的工程范式：`page → viewmodel → use case → repository → HTTP data source`，AI 回复为非流式或 SSE 流式。
2. **提示词工程**：系统提示词绑定量表模板，要求模型输出**结构化 JSON**（各维度得分、分级、依据、追问项），App 解析渲染成评估表单卡片。对话轮次控制在 8-12 轮内完成采集。
3. **计划生成**：模型依据评估结果生成 A/B/C 三套计划（基础照护型 / 防跌加强型 / 康复促进型），每套含巡视频率、监测设备配置建议、活动安排。对应现有 `AdmissionCarePlan`/`CarePlanSuggestion` 数据结构，UI 已有推荐与知情确认字段。
4. **降级策略**：模型服务不可用时，回落到内置规则引擎（阈值查表）生成计划，保证演示不中断。

### 4.3 演示要点

- 平板宽屏演示医生工作台对话+评估表单联动（左对话右表单）。
- 手机端演示护理员视角查看已确认计划。
- 讲稿强调：量表对齐国标、AI 只建议医生拍板、全程留痕。

## 五、场景二：毫米波雷达持续监护（防跌倒/呼吸/心率）

### 5.1 设备与点位

| 点位 | 设备 | 核心数据 |
|------|------|---------|
| 卧室（床头对侧墙上） | R60ABD1 睡眠呼吸心率雷达 | 呼吸值（0-40 次/min，正常 10-25）、心率（60-120 次/min）、睡眠状态（深睡/浅睡/清醒/离床）、睡眠评分、呼吸暂停次数、体动 |
| 卫生间（顶装） | R60AFD1 跌倒检测雷达 | 跌倒状态 fallStatus、跌倒位置 fallPosition、静止驻留 residentStatus、灵敏度 0-3 |

毫米波相对摄像头的核心优势（答辩必讲）：**非接触、无隐私暴露、不受光照影响、卫生间可用**——恰好补足摄像头不能装的场所。

### 5.2 数据链路

```
雷达(每房间) → EMQX Broker(1883) → 后端网关(订阅+房间路由) → WebSocket → 鸿蒙App实时看板
```

1. **协议要点**（来自 `MTQQ/` 厂商文档，已本地验证）：睡眠雷达 topic `/Radar60SP/{设备ID}/sys/property/post`，跌倒雷达 `/Radar60FL/{设备ID}/sys/property/post`；数值字段为字符串需转换；波形类字段为数组。
2. **房间路由**：复用 `mqtt_bridge_demo.py` 的路由逻辑（topic 取设备 ID → 查绑定表 → 定房间/老人）。生产化时把 `room_device_map.json` 换成数据库表，比赛演示用 JSON 即可。
3. **设备初始化**：按 `init_commands.txt` 下发 sceneMode（卧室=2、卫生间=3）与 installHeight，保证算法匹配场景，压低误报——这是厂商文档明确强调的步骤。
4. **App 端接入**：声明 INTERNET 权限，`@ohos.net.webSocket` 订阅网关。现有 DeviceListCard/HealthListCard 的 mock 字段名与雷达协议**同名**（humanDistance/motionStatus 等），替换成本低。

### 5.3 告警规则（演示版）

| 触发条件 | 级别 | 动作 |
|---------|------|------|
| fallStatus=1 | 紧急 | App 红色弹窗 + 蜂鸣 + 推送摄像头 VL 复核 |
| 呼吸 <10 或 >25 次/min | 高 | App 橙色告警，值班护理员确认 |
| 心率 <50 或 >120 次/min | 高 | 同上 |
| 夜间离床 >15 分钟未归 | 中 | 提醒巡逻查看 |
| 卫生间静止驻留超阈值 | 中 | 提醒查看 |

所有告警进入事件库，处置结果（到场/误报/处理）回填，形成留痕闭环。

## 六、场景三：摄像头 + VL 模型行为识别

### 6.1 方案定位

摄像头装在**公共活动区与卧室门口**（卫生间只用毫米波，伦理红线）。视频流**不出边缘主机**：抽帧推理、只输出结构化行为事件，原始画面仅本地循环存储，这是隐私架构的核心卖点。

### 6.2 模型选型

| 候选 | 规格 | 优劣 |
|------|------|------|
| Qwen2.5-VL-7B（首选） | 单卡消费级 GPU 可跑量化版 | 中文强、图像+视频理解、Apache 2.0 可商用 |
| MiniCPM-V 2.6（备选） | 8B，端侧友好 | 更轻，复杂行为判别弱一档 |
| InternVL2.5-8B（备选） | 8B | 综合均衡 |

推理服务封装为：**输入**=抽帧序列（1-2 fps）+ 受控行为类别表；**输出**=JSON（行为类别、置信度、时间戳、房间）。用受控类别表（closed-set）+ JSON Schema 约束输出，压制模型幻觉。

### 6.3 行为类别体系（v1 演示版）

| 类别组 | 行为 | 响应 |
|--------|------|------|
| 正常 | 行走、坐立、卧床、进食、如厕（判为卫生间停留） | 看板静默记录 |
| 关注 | 久坐不动 >30min、夜间离床未归、徘徊（认知障碍特征） | 中级提醒 |
| 告警 | 跌倒疑似、剧烈挣扎 | 触发交叉验证 |

### 6.4 与毫米波交叉验证（多模态融合，答辩亮点）

单传感器误报是行业公认痛点（跌倒检测误报会让护理员麻木）。融合规则：

1. **毫米波 fallStatus=1** → 边缘服务推送对应房间摄像头最近 5 秒关键帧给 VL 复核 → VL 判定"跌倒姿态" → **高置信告警**（双确认）。
2. VL 疑似跌倒 + 毫米波无检测 → **低置信提醒**（人工复核队列）。
3. 两者皆无 → 静默。持续记录"行为-生命体征"关联基线，用于计划修订（如夜间频繁离床 → 调整计划）。

### 6.5 演示降级预案

时间不允许部署 GPU 时：预录行为识别视频 + 现场跑离线推理回放；架构图讲清部署路径。毫米波场景不受此影响，始终真数据。

## 七、端到端工作流设计

### 7.1 六阶段闭环

1. **入院受理**：建档、设备绑定（房间台账登记设备 ID）。
2. **AI 评估**：对话式量表采集 → 结构化评估结果。
3. **计划生成与选择**：A/B/C 计划 → 医生确认 → 下发监测配置（雷达灵敏度、告警阈值随计划档位联动）。
4. **持续监护**：毫米波生命体征 + VL 行为事件实时汇聚，看板呈现。
5. **事件处置**：分级告警 → VL 交叉复核 → 护理员处置 → 结果回填。
6. **数据回流**：周报自动生成（睡眠评分趋势、跌倒风险动态、计划执行率）→ 触发计划复查建议 → 回到阶段 3，形成闭环。

### 7.2 关键接口约定（演示版）

| 接口 | 方向 | 协议 | 内容 |
|------|------|------|------|
| 设备属性上报 | 雷达→Broker | MQTT | JSON，topic 按设备 ID 路由 |
| 实时数据推送 | 网关→App | WebSocket | 心跳/数值/事件帧，按房间+老人聚合 |
| 对话请求 | App→推理服务 | HTTP(S) | 评估上下文 + 量表模板 |
| 行为事件 | VL 服务→网关 | HTTP | JSON（类别/置信度/时间戳/房间） |
| 告警确认 | App→网关 | WebSocket | 处置结果回填 |

### 7.3 演示时序（四设备同屏）

平板（医生评估）→ 手机（护理员告警处置）→ 大屏（看板：雷达数值滚动 + 摄像头行为事件流）→ 讲解端（架构图随场景高亮）。

## 八、安全与隐私合规方案

### 8.1 数据分级

| 级别 | 数据 | 处置原则 |
|------|------|---------|
| L4 高敏 | 摄像头画面 | 边缘处理不出内网、循环覆写 ≤7 天、App 默认骨架化/区域框展示、物理遮挡开关 |
| L3 敏感 | 生命体征、健康评估、位置 | 加密存储、授权可见、家属按知情范围查看 |
| L2 业务 | 任务、排班、告警记录 | 角色权限控制 |
| L1 公开 | 界面文案、科普内容 | 常规管理 |

### 8.2 合规基线

对标《个人信息保护法》《数据安全法》及 GB/T 35273-2020《个人信息安全规范》：健康与行踪数据属敏感个人信息，处理需**单独同意**；入院协议中列明监测项、数据用途、家属可见范围、退出机制（一键降级为仅毫米波模式）。

### 8.3 技术措施

1. **传输**：MQTT 启用账号鉴权，演示局域网内明文可接受但需 UI 标注（沿用 hermes 的"明文仅限可信局域网"警告模式）；生产化上 TLS。
2. **存储**：评估记录与告警留痕本地加密；token 仅进程内存不落盘（hermes 已验证模式）。
3. **权限最小化**：App 仅声明 INTERNET；摄像头不进端侧权限链路。
4. **审计**：告警确认、计划修改、数据导出全留痕。
5. **比赛演示伦理**：所有"老人"由志愿者扮演，跌倒用安全垫+慢动作，现场向评委说明知情同意流程，演示数据赛后清除。

### 9.1 公开数据集（预训练与评估基准）

| 数据集 | 用途 |

### 9.2 自建数据集（赛后规模化，比赛讲规划）

1. **类别体系**：按第六章 v1 行为表，扩展至 20 类（含细分姿态与过渡动作）。
2. **采集协议**：多房型（单人间/双人间）、多光照（昼夜）、多视角；志愿者+受训演员在安全垫上模拟跌倒；每段 30-120 秒，同步记录毫米波 JSON 流（fallStatus 天然弱标注）。
3. **标注规范**：时间段级标注 + 抽帧复核；双人独立标注，Cohen's Kappa ≥0.8 仲裁；边界帧逐帧裁定。
4. **规模路线**：演示级 2000 段 → 半年 10000 段；毫米波数据随部署持续积累，与视觉样本按设备 ID+时间戳对齐。
5. **数据治理**：采集全程书面知情同意；人脸区域默认模糊化；数据分级入库，与第八章对齐。

### 9.3 评估基准

| 指标 | 目标（演示→产品） |
|------|------------------|
| 跌倒召回率（灵敏度） | ≥95%（双模融合） |
| 误报率 | <2 次/房间/天（融合后较单模降一个数量级） |
| 端到端告警延迟 | <3 秒（事件→App 弹窗） |
| 呼吸/心率误差 | 与厂商规格一致（±1 次/min 量级，引用厂商标称） |
